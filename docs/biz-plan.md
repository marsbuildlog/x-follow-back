# Twitter 自动回关插件

## 背景

最近简中 X 圈发起了蓝V互关风潮, 但是 Twitter 目前回关或者关注别人会有一个频率限制, 所以如果你有较多人关注的话, 回关需要过一会儿再手动操作一下。

目标用户往往粉丝量较大, 粉丝中混杂大量垃圾账号, 因此不能盲目回关全部粉丝。

## 目标 / 非目标

### 目标

- 自动回关全部认证粉丝(蓝V), 替代手动操作
- 遵守关注频率限制, 控制账号风险
- 可视化查看回关进度与状态

### 非目标 (本期不做)

- 普通粉丝(无认证)的回关
- 多账号支持
- 取关不回关的人等反向功能
- 历史记录展示
- 自动定时触发(后续可加)

## 决策记录

| # | 决策 | 理由 |
|---|------|------|
| 1 | 只处理认证粉丝 | 用户粉丝量大、垃圾账号多, 全量回关会关注一堆垃圾号; 蓝V是天然的质量过滤 |
| 2 | 不设客户端每日上限 | X 侧会自行限流: 触达关注上限(错误码 161)时任务暂停至次日, 客户端重复设限无意义; 保留今日计数仅作展示 |
| 3 | 持续 30 分钟无法关注则暂停任务 | 判定为被限流, 先暂停避免风险 |
| 4 | 多账号暂不处理 | 只处理当前登录账号 |
| 5 | 不做历史记录展示 | 失败时展示出错信息即可 |
| 6 | UI: 独立 options 页 + x.com 页面顶部注入状态条 | 状态条展示当前进度、今日关注数 |
| 7 | 关注间隔随机 3~8 秒 | 默认值随实测调快: 30~90 → 15~30 → 3~8(2026-10); 过快有账号风险, 可在设置里调回 |
| 8 | 暂停后手动恢复; 未手动恢复则每隔 1 小时自动尝试恢复 | 兼顾人工控制与无人值守 |
| 9 | 浏览器范围: Chrome + Edge (均为 MV3) | 不做 Firefox |
| 10 | 429 恢复按响应头 x-rate-limit-reset 精确等待 | 窗口剩余/重置时刻在响应头里(x-rate-limit-remaining/reset), 无需猜退避时长; remaining=0 时主动等重置避免吃 429; 无头时退回固定退避(设置项) |
| 11 | 已关注过滤只信 BlueVerifiedFollowers 自带字段, 不拉 following/list.json | 旧方案(following/list 交集)从未验证跑通过; 冗余翻页浪费限流额度; 字段实测稳定, 缺失时首页诊断日志(followFields)可见 |
| 12 | 拉取器与回关循环解耦(生产者/消费者) | 拉取吃 429 不应连坐回关任务; 队列纯追加合并, 天然无写冲突 |
| 13 | 拉取自动化: 打开页面且距上次拉取超过 autoFetchMin(默认30分钟)自动拉一次, 手动拉取重新计时 | 新粉丝自动入队, 等待新粉状态自动续跑, 接近无人值守 |
| 14 | 数据按账号分键(rf_task:{handle}/rf_daily:{handle}) | 换账号不再清队列; 仍只跑当前登录账号, 不算多账号功能 |
| 15 | 关注上限提高到5万(500页×100/页); 展示只保留总数/待回关/今日数 | 部分用户粉丝量大; 其他统计不重要, 但每人状态/出错/完成时间仍全量记录 |
| 16 | 429 不标失败, 等待后重试同一人, 连续 3 次才跳过 | 限流是环境问题不是这个人的问题, 标失败会让被限的人丢失直到手动恢复 |
| 17 | 403(模板过期)立即暂停 template-expired, 不自动恢复 | 空转烧请求; 用户点一次「回关」刷新模板后手动恢复 |
| 18 | 请求层连续异常 2 次暂停 + 通知; 所有自动暂停发系统通知(带声音) | 避免静默死亡循环/空转烧请求; 否则用户以为还在正常跑 |
| 19 | 403 先解析错误码: 161→今日上限暂停, 无已知码→才判模板过期 | 实测 161 包在 HTTP 403 里返回, 先看状态码会误判为模板过期(2026-10 实跑样本) |

## 核心流程

生产者/消费者架构, 拉取与回关解耦:

1. **拉取器(生产者)**: 通过 https://x.com/{handle}/verified_followers 页面接口拉取认证关注者(100/页, 上限500页)
   - 触发: 手动「更新列表」/ 打开页面且距上次拉取超过 autoFetchMin(默认30分钟, 手动拉取后重新计时)
   - 拉取中吃 429 自行退避重试, 不影响回关任务
   - 已关注过滤只信接口自带的 `relationship_perspectives.following`
2. **队列**: 拉取结果纯追加合并进待回关队列(不碰已有条目), 按账号分键存储
3. **回关循环(消费者)**: 只消费 pending, 逐个发起关注:
   - 每次关注之间随机间隔 3~8 秒(模拟人工)
   - 队列空 → done(等待新粉), 拉取器写入新 pending 后自动续跑
   - 失败按类型处理(见下方"失败处理策略")
   - 持续 30 分钟无法成功关注 → 暂停任务; 手动恢复, 若未手动恢复则每隔 1 小时自动尝试恢复
   - 触达 X 侧关注上限(错误码 161) → 暂停任务至次日
4. 任务状态持久化到 chrome.storage.local(按账号分键), 浏览器/插件重启后可恢复

## 失败处理策略

> 目前不明确接口会有哪些失败返回, 先按大类处理, 并把原始错误信息展示在 options 页, 等真实运行收集到样本后再细化分类。

| 类型 | 判定(初步) | 处理 |
|------|-----------|------|
| 限流 | HTTP 429 / rate limit 错误码 | 退避重试; 持续 30 分钟未恢复则暂停任务 |
| 受保护账号 | protected account 相关错误 | 标记为跳过 |
| 已关注 / 账号不存在 | already following / not found | 标记为完成或跳过 |
| 未知错误 | 其他 | 记录并展示原始错误信息, 短间隔重试若干次 |

## UI

### options 页(独立页面)

- 概要: 账号 / 状态(运行中/暂停/等待新粉/未启动) / 总数 / 待回关 / 今日已回关 / 上次拉取时间
- 队列表(记录全量): 每人一行, 含状态(待处理 / 成功 / 失败 / 跳过)与出错信息
- 暂停时提供手动"恢复"按钮
- 设置: 间隔/退避/自动拉取间隔

### x.com 页面注入状态条

- 打开 verified_followers 页面时, 在页面顶部注入基本状态:
  - 状态(含等待新粉/暂停倒计时) · 总数 · 待回关 · 今日已回关数
  - 按钮: 开始回关 / 更新列表 / 暂停 / 恢复

## 技术方案

- 浏览器: Chrome + Edge, 均为 MV3
- 存储: chrome.storage.local
- 任务执行: 绑定在打开的 x.com 标签页内运行(content script / 页面注入脚本), 避免 MV3 service worker 被回收导致任务中断
- 接口: 复用页面登录态(cookie + csrf token)调用 x.com 的 GraphQL 接口

## PoC 结论(已实测验证)

| 风险点 | 结论 |
|--------|------|
| x-client-transaction-id 无法自行构造 | 已解决: 在 x.com 页面上下文内捕获页面自身请求的完整请求头并原样重放; 回关模板持久化到 localStorage, 重放时自动刷新 csrf token, 过期时(403)提示手动点一次「回关」刷新 |
| 认证粉丝分页 | 可翻页拉全: `BlueVerifiedFollowers`(GraphQL), count=100/页有效; 注意列表拉完后接口仍返回 cursor, 以「一页 0 人」作为终止条件 |
| 关注接口 | 实际是 v1.1 REST `POST /i/api/1.1/friendships/create.json`(非 GraphQL), body 为 x-www-form-urlencoded, 仅替换 user_id 即可重放, 返回 200 且真实生效 |
| 已关注状态 | 直接用 BlueVerifiedFollowers 自带的 `relationship_perspectives.following` 过滤已关注; 不拉 following/list.json(旧方案未验证跑通过, 已移除) |
| 任务运行环境 | 绑定 x.com 标签页内运行; 插件重载后孤儿脚本自动清理, 新实例自动接管未完成任务 |

实测数据: 277 个认证粉丝, 跳过已关注 135 个, 待回关约 142 个, 重放关注真实生效。
