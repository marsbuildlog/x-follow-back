# SearchTimeline 重放: 单 tid 冷却与参数硬约束

互关帖的搜索/扫描阶段靠重放页面捕获的 SearchTimeline 请求(固定复用捕获的那个 x-client-transaction-id)。2026-10-10 用真实请求对照实验(18 组)钉死了 X 对这个端点的几条隐藏规则, 404 之谜的根源是第一条。

## 实测规则(2026-10-10)

- **同 tid 成功冷却**: 同一 x-client-transaction-id 的请求成功后约 60 秒内(实测 ≤68 秒), 同 tid 的任何请求一律 HTTP 404(空 body)——**字节相同的原样重放也不例外**; 失败的请求不延长冷却。页面自身每次请求生成新 tid, 故页面自己翻页永远正常; 重放固定复用 tid, 所以"第 1 页成功后 2 秒发第 2 页"必然 404——这是长期误判为"queryId 轮换/参数错误"的真因。
- **count 必须是 20**: 21/40/100 全部 404, 无错误信息。`AF.SEARCH_PAGE_SIZE` 不可改。
- **tid 必须存在**: 不带 x-client-transaction-id 直接 404; 但 tid 不绑定 URL, 复用最近捕获的即可, 也允许换到同路径的其它查询上用。
- **宽松项**: cursor 值可复用(跨会话也行)、variables 的 JSON 键序无关、查询词任意(不存在的词返回 200 空结果)、重编码只要语义等价即可。
- **对照实验的解读**: 冷却期内原样重放必然也 404, 它只能区分"传输层完全坏"与"冷却/参数", 不能证明参数有问题。

## Decision

- `searchPage` 每次发射前确保距"捕获时刻"与"上次重放成功"都满 `AF.TID_COOLDOWN_MS`(70 秒, 实测上限 68 秒留余量), 不足则打日志等待。
- 冷却等待使翻页间隔拉到约 70 秒/页, 接受此代价(搜索 10 页 ≈ 12 分钟, 扫描通常 1-2 页)。

## Considered Options

- **等待冷却**(采纳): 改动最小, 行为可预期。
- **搜索单不用重放**(备选): page-hook 捕获页面自己的响应体, 用户滚动页面即翻页, 零重放零风险; 待重放路线再撞墙时启用。
- **自研 transaction-id 生成器**(拒绝): 要追 X 的挑战文件轮换, 维护成本高。
- **改 count 提速**(拒绝): count≠20 直接 404, 无此自由度。

## Consequences

- 翻页型任务(搜索/扫描)每页 ≥70 秒; 日志出现"同tid冷却中"属预期行为, 不是卡死。
- 若未来 X 调整冷却时长, 症状是"等待 70 秒后仍 404"——先用对照实验区分冷却与参数, 再重测本 ADR 的规则。
